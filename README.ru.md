# zIPAM

[English](README.md) | [Русский](README.ru.md)

Open-source-платформа IP Address Management (IPAM): сильная поддержка
IPv4/IPv6, иерархия префиксов, аллокация с гарантиями корректности на уровне
базы данных, современный веб-интерфейс.

> **Статус (цикл rc-01):** аутентификация и модель ролей, справочники, ядро
> IPAM (префиксы, IP-адреса, аллокация/освобождение, утилизация, поиск),
> рабочий веб-интерфейс и Docker-стек доступны уже сейчас. REST API —
> **черновой** (контракт стабилизируется к 1.0.0); аудит и OpenAPI — в
> следующем цикле.

## Что делает zIPAM

- Учит **префиксы** (сети) в иерархии, которая выводится из самого адресного
  пространства — дерево не ведётся вручную, его корректность обеспечивает
  PostgreSQL.
- Учит **IP-адреса** внутри префиксов: аллокация, резервирование,
  освобождение. Аллокация транзакционна: два параллельных запроса никогда не
  получат один и тот же адрес.
- IPv4 и IPv6 — полноценные граждане первого класса (строгий CIDR,
  сжатие по RFC 5952).
- Поддержка **VRF** и **VLAN**; принадлежность через организации, тенанты,
  регионы и площадки (sites).
- Визуализация утилизации и сетка адресов для небольших префиксов.
- Глобальный **поиск** по IP, CIDR или имени.
- Веб-интерфейс на сессионной аутентификации с ролевой моделью; любая
  операция доступна и через REST API.

# Руководство пользователя

## Вход

Откройте адрес приложения (по умолчанию `http://localhost:8080`) и войдите с
логином и паролем, выданными администратором. Сессия хранится в HTTP-only
cookie; завершить её — кнопка **Log out** в верхней панели.

## Роли

| Роль | Что может |
|---|---|
| **viewer** | просматривать всё; создание/изменение/удаление недоступны нигде |
| **operator** | всё, что viewer, плюс вся операционная работа: создавать/править префиксы, выделять/освобождать адреса, вести справочники |
| **admin** | управление пользователями и группами (через Django admin); фактически обладает и остальными ролями |

Роли проверяются на бэкенде — скрытие кнопок в интерфейсе никогда не является
единственной защитой. Попытка записи без прав возвращает `403`.

## Основные понятия

| Объект | Значение |
|---|---|
| **VRF** | независимое адресное пространство. Уникальность префиксов и адресов контролируется *в пределах VRF*, поэтому пересекающиеся префиксы в разных VRF — это нормально. Непрочитываемый дескриптор маршрутизации (`rd`) — опционально. |
| **Префикс** | сеть в строгой CIDR-нотации (например `10.10.0.0/24` — хостовые биты должны быть нулевыми; `10.10.0.1/24` будет отклонён). Статусы: `active`, `reserved`, `container` (держатель пространства, сам хосты не несёт), `deprecated`. Опционально привязывается к тенанту и площадке. |
| **IP-адрес** | запись об аллокации внутри VRF. Статусы: `active`, `reserved`, `deprecated`. Удаление адреса = его освобождение. |
| **VLAN** | `vid` 1–4094 и имя; уникальность по паре (vid, name). |
| **Organization / Tenant / Region / Site** | справочные объекты принадлежности и расположения префиксов. |

Иерархия префиксов строится автоматически по вложенности: `10.10.1.0/24`
внутри `10.10.0.0/16` внутри `10.0.0.0/8`. Родители, дети, свободное
пространство и утилизация вычисляются базой данных, а не клиентом.

Типовой рабочий процесс: создать VRF (или использовать встроенный `global`) →
создать префиксы верхнего уровня → при необходимости разбить их → выделять
адреса по мере надобности.

## Префиксы

Страница **Prefixes** (она же стартовая) показывает все префиксы с
серверной пагинацией.

- **Фильтры** — по VRF, по статусу и **Contains**: введите любой IP или CIDR
  (`10.0.0.5`, `10.0.0.0/24`) — получите всех его предков; быстрый ответ на
  вопрос «какой сети принадлежит этот адрес».
- **Создание префикса** — выберите VRF (обязательно), введите префикс в
  строгом CIDR (форма подскажет, если он не строгий), при желании укажите
  статус, тенант, площадку и описание. Дубликаты внутри VRF отклоняются.
- Клик по строке открывает страницу **префикса**.

## Страница префикса

Рабочее место одного префикса:

- **«Хлебные крошки»** предков и список **детей**.
- **Полоса утилизации** — выделено / всего адресов, свободно, процент.
- **Выделить адрес** — укажите статус и описание; сервис вернёт ближайший
  свободный адрес. Сетевой адрес и адрес широковещательной рассылки (IPv4 ≤
  `/30`), а также anycast-адрес subnet-router (IPv6) пропускаются
  автоматически.
- **Сетка адресов** — для префиксов до 1024 адресов: каждый адрес — цветная
  ячейка. Клик по свободной ячейке выделяет ровно этот адрес; клик по занятой
  — редактирование статуса/описания или освобождение.
- **Таблица адресов** — для префиксов любого размера (виртуализация,
  пагинация): огромные сети не подвешивают интерфейс.
- **Разбиение префикса (split)** — деление на детей указанной длины маски.
  Разрешено, только если у префикса нет детей и выделенных адресов.
- **Доступные подсети** — список свободного пространства внутри префикса,
  при желании для конкретной длины маски (например «какие свободные /26
  остались»).
- **Изменить** статус/описание или **Удалить** префикс (с подтверждением;
  его адреса удаляются вместе с ним). Удаление префикса, у которого остались
  дети-префиксы, запрещено — сначала удалите детей.

## IP-адреса

Страница **IP Addresses** работает по всем префиксам сразу:

- Фильтры: VRF, статус, точный адрес, **within** по CIDR.
- Отметьте строки и нажмите **Release selected** — массовая операция, которая
  честно сообщает о частичных ошибках вместо молчаливого пропуска.
- Инлайн-редактирование статуса/описания.
- Результаты поиска ссылаются на эту страницу с уже подставленным адресом.

Адреса обычно создаются со страницы префикса (выделение). Чтобы внести в
инвентарь конкретный адрес, кликните его ячейку в сетке адресов.

## Поиск

**Search** (`q` в боковой панели, минимум 2 символа) отвечает группами:

- IP-адрес (`10.0.0.5`) → найденная аллокация плюс все содержащие его
  префиксы;
- CIDR (`10.0.0.0/24`) → пересекающиеся префиксы и адреса;
- произвольный текст → имена префиксов, VRF, VLAN (по VID), организаций,
  тенантов, регионов, площадок.

Каждая находка ведёт сразу на нужную страницу.

## VRF, VLAN и справочники

**VRFs**, **VLANs**, **Organizations**, **Tenants**, **Regions** и **Sites** —
простые страницы «список + форма»: создание, редактирование, удаление. Два
правила, которые стоит помнить:

- VRF нельзя удалить, пока в нём остаются префиксы или адреса;
- тенант/площадку/регион/организацию нельзя удалить, пока на них ссылаются
  префиксы (API отвечает `409 REFERENCE_PROTECTED`).

## REST API (черновой)

Всё, что умеет интерфейс, доступно под `/api/v1/`. Контракт черновой до 1.0.0.
Быстрая карта:

```
POST /api/v1/auth/login            GET  /api/v1/auth/me
GET  /api/v1/prefixes/?vrf=&status=&tenant=&site=&contains=&within=&parent=
GET  /api/v1/prefixes/{id}/utilization/
POST /api/v1/prefixes/{id}/allocate/          {"status": "active", "description": "..."}
POST /api/v1/prefixes/{id}/split/             {"prefix_len": 26}
POST /api/v1/prefixes/{id}/available-subnets/ {"masklen": 26}
GET  /api/v1/ip-addresses/?vrf=&status=&address=&within=
GET  /api/v1/search/?q=10.0.0.5
```

Сессионная аутентификация с CSRF-защитой (браузерный клиент делает оба шага
сам; для скриптов сначала получите `GET /api/v1/auth/csrf` и передайте токен в
заголовке `X-CSRFToken`). Ошибки используют единый конверт со стабильными
машинночитаемыми кодами — интеграции стройте на коде, а не на тексте
сообщения:

```json
{
  "error": {
    "code": "IP_ALREADY_ALLOCATED",
    "message": "The requested IP address is already allocated.",
    "details": {}
  }
}
```

Списочные эндпоинты пагинированы (`page`, `page_size` до 1024).

# Руководство администратора

## Требования

Docker с плагином Compose. Больше никакого ПО на хосте не нужно.

## Установка

```bash
cp .env.example .env    # затем отредактируйте — см. таблицу ниже
docker compose up -d --build
```

Поднимаются три контейнера: PostgreSQL 16, бэкенд на Django и nginx, который
отдаёт интерфейс и проксирует `/api`, `/health`, `/ready` на бэкенд. Откройте
`http://<host>:8080` (порт настраивается через `ZIPAM_WEB_PORT`).

## Конфигурация (`.env`)

| Переменная | По умолчанию | Примечание |
|---|---|---|
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | `zipam` / `zipam` / — | **задайте настоящий пароль**; том базы данных сохранит его |
| `ZIPAM_PG_HOST_PORT` | `5433` | порт хоста, на котором публикуется БД |
| `DJANGO_SECRET_KEY` | — | **обязательна**, ≥ 50 случайных символов, например `python3 -c "import secrets; print(secrets.token_urlsafe(64))"` |
| `DJANGO_SETTINGS_MODULE` | `config.settings.dev` | production-конфиг появится позже |
| `DJANGO_ALLOWED_HOSTS` | `localhost,127.0.0.1,backend,frontend` | добавьте своё имя хоста |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | `http://localhost:8080` | **должно содержать точный URL, по которому заходят пользователи** (scheme + host + port, например `http://localhost:8088`) — иначе логины из браузера падают с CSRF-ошибкой |
| `ZIPAM_WEB_PORT` | `8080` | публикуемый порт интерфейса |
| `ZIPAM_LOG_LEVEL` | `INFO` | |

## Пользователи и роли

UI для управления пользователями пока не реализован; пользователи
управляются из командной строки:

```bash
# создать superuser (получает все роли)
docker compose exec backend python manage.py createsuperuser

# задать пароль
docker compose exec backend python manage.py changepassword <username>

# создать обычного пользователя и назначить роль
docker compose exec backend python manage.py shell -c '
from django.contrib.auth.models import User, Group
u = User.objects.create_user("alice", password="<password>")
u.groups.add(Group.objects.get(name="operator"))'
```

Три группы ролей (`viewer`, `operator`, `admin`) создаются миграцией;
superuser обладает всеми ролями неявно. Django admin в стандартном compose не
проброшен через веб-прокси — управляйте пользователями командами выше либо
добавьте прокси-location / опубликуйте порт `8000` сами.

## Health и readiness

```
GET /health   живость процесса
GET /ready    готовность, включая доступность базы данных
```

У всех трёх сервисов есть Docker health checks; состояние видно в
`docker compose ps`.

# Руководство разработчика

## Стек

- Бэкенд: Python 3.12, Django 5, Django REST Framework, PostgreSQL 16
- Фронтенд: React + TypeScript (strict) + Vite + TailwindCSS
- Гейты качества: ruff, mypy, pytest / eslint, tsc, vitest

## Разработка бэкенда

```bash
cd backend
uv venv --python 3.12 .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
docker compose up -d db
export POSTGRES_HOST=localhost POSTGRES_PORT=5433 POSTGRES_DB=zipam \
       POSTGRES_USER=zipam POSTGRES_PASSWORD=<from .env>
python manage.py migrate
python manage.py runserver
ruff check . && mypy config core apps && pytest
```

## Разработка фронтенда

```bash
cd frontend
npm ci
npm run dev        # http://localhost:5173 (proxies /health,/ready,/api)
npm run lint && npm run typecheck && npm test
```

## Архитектура в четырёх пунктах

- View'ы тонкие; вся бизнес-логика — в `services.py` приложений
  (`allocate_ip`, `split_prefix`, `calculate_utilization`, …).
- Сетевая корректность живёт в PostgreSQL: собственные `inet`-поля с
  GiST-индексами, иерархия через нативные операторы (`>>`, `<<`, `&&`, …),
  уникальность через `UNIQUE(vrf, prefix)` / `UNIQUE(vrf, address)`.
  Аллокация берёт блокировку строки префикса, поэтому параллельные аллокации
  сериализуются — см. ADR и `core/db/`.
- Доменные ошибки отображаются в стабильные коды через общий `DomainError` и
  документированный конверт ошибок.
- Фронтенд организован по фичам (`src/features/...`); весь контакт с
  библиотекой таблиц/виртуализации изолирован в generic `DataTable`.
